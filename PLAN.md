# Boat Spot Finder — Master Implementation Plan

## Context

The project is fully documented and scaffolded but contains zero domain code. All five entities, the DbContext, Identity setup, repositories, services, controllers, and views are yet to be built. This plan is the master roadmap: it tracks every phase and task, maps the dependency graph, and specifies exactly what files each `/dev` brief must produce. Update the status of each task here as work is approved.

Status legend: `[ ]` not started · `[x]` complete · `[~]` in progress

## Mandatory Step Workflow

**Every `/dev` brief must be followed by `/verify` before anything else proceeds.**

| Step | Command | When |
|------|---------|------|
| Implement | `/dev <brief>` | Tech lead writes and delegates the brief |
| Verify | `/verify <brief>` | Immediately after Dev reports done — checks correctness, conventions, and build |
| Mark task complete | Update `[ ]` → `[x]` in this file | Only after `/verify` returns Approved |
| Document | `/doc <phase summary>` | Once **all tasks in the phase** are approved — one `/doc` call per phase, covering the full feature set |

If `/verify` returns **Needs rework**, write a correction brief and run `/dev` again. Do not mark the task complete or move to the next task until verification passes.

**Documentation is per phase, not per task.** Calling `/doc` after every brief produces fragmented docs. Wait until every task in the phase has an `[x]`, then run one `/doc` that describes the entire phase — entities, repositories, services, controllers, and views together.

**Notes:**
- **FK types to `ApplicationUser` are `string`, not `Guid`.** `IdentityUser.Id` is `string`. Every FK that points at `ApplicationUser` must be declared as `string`: `MarinaAdmin.UserId` (`string`), `MarinaAdmin.InvitedById` (`string`), `Invitation.InvitedById` (`string`), `Booking.BoatOwnerId` (`string`), `Vessel.OwnerId` (`string`). Do not use `Guid` for any of these — it will cause a migration/schema mismatch with the Identity tables.
- `ApplicationUser` extending `IdentityUser` pulls only `Microsoft.Extensions.Identity.Core` into Core — no EF dep, layering rule is upheld.
- `Microsoft.AspNetCore.Identity.EntityFrameworkCore` must be on Infrastructure (where AppDbContext lives), not only Web.
- Admin user seed: use the pre-generated hardcoded hash literal specified in task 1.3 directly in the `HasData` call. Never call `PasswordHasher` inside `OnModelCreating` — the random salt means every subsequent migration add produces a new hash and a spurious update migration. Use a fixed GUID for idempotency.
- EF Core 10 natively supports `DateOnly` with SQL Server — no value converter needed.
- Canvas coordinates use a fixed logical unit system (e.g. 0–1200 × 0–800). The frontend scales these to the actual rendered canvas size client-side.
- `Invitation.Token` stored as SHA-256 hash; raw token sent in the email link only.
- `SpotSeasonalRule` date ranges must not overlap for the same spot — enforced at service layer (reject save if any existing rule's range intersects the new one).

## Phase 2c — Audit Log Search & Admin Viewer

**Goal:** Make the audit trail queryable by Admins through a filterable grid — **without putting audit data in SQL Server**. The daily JSON audit files remain the permanent, immutable system of record (never deleted by the app). Elasticsearch holds a **rolling 30-day projection rebuilt entirely from those files**, so ES is a disposable cache: if it is wiped or disabled the audit record is untouched and the window self-heals on the next reconcile.

**Design:**
- **Files = source of truth.** `logs/audit-{yyyy-MM-dd}.log` (JSON-lines, UTC) are append-only and never pruned by the app. SQL Server holds no audit data.
- **ES = derived 30-day window.** Entries are indexed into daily ES indices `audit-{yyyy.MM.dd}`; indices older than 30 days are dropped. NLog never writes ES directly — ES is rebuilt from the files by Hangfire jobs.
- **Idempotent indexing (load-bearing).** Every audit entry carries a unique `eventId` (Guid) emitted at write time. ES documents use `eventId` as `_id`, so re-indexing the same file line is an upsert, never a duplicate. This is what makes the every-2-minute job safe.
- **Two Hangfire jobs.** `audit-reindex-today` (every 2 min) upserts today's file; `audit-reconcile-window` (nightly 03:00 UTC) re-upserts the last 30 days and drops indices older than 30 days.
- **Admin grid.** `/admin/audit-log` — filterable, paginated, querying ES through `IAuditLogSearchService`. Degrades gracefully in Mode 1 (ES off) with a notice. ES is queried only through the app — never exposed directly.
- **Mode 1 (no ES).** All ES paths no-op via the null stub; the grid shows an "audit search unavailable" notice. File logging is unaffected.

**Goal:** PlaceOwners manage their own marinas and spots. Each marina has a canvas-based layout editor where spots (rectangles) are drawn and positioned. Ownership enforced on every action.

**Marina lifecycle:** Admin creates marina (name + region only) → Admin invites PlaceOwner for that marina → PlaceOwner fills in full details (description, address, phone, lat/lng) + designs layout. Marinas are never hard-deleted — Admin can deactivate them.

**PlaceOwner flow:** Receives invite link → registers → lands on their marina's Edit page to complete info → then opens Layout Editor to design spots.

**Ownership check (all PlaceOwner actions):** verify `MarinaAdmin` record exists for `(marinaId, currentUserId)` — not a single FK. Return `Forbid()` if not found.

## Phase 5b — Reviews & Ratings

**Goal:** Bidirectional post-stay reviews. A completed booking unlocks one review per party: BoatOwner rates the Marina; PlaceOwner rates the BoatOwner. Ratings are denormalized onto their SQL entities and reflected in the Marina ES document. All reviews are indexed in a new `reviews` ES index. Review window: 14 days from `Booking.EndDate`.

**Review invariants:**
- Only `Status == Completed` bookings can be reviewed.
- Unique constraint on `(BookingId, ReviewerRole)` — one review per direction per booking. No edits or deletes.
- Review deadline: `Booking.EndDate.AddDays(14)`. Checked in `ReviewService.CanReviewAsync`. After deadline, Create returns 404.
- Marina rating = average of all `Score` values where `ReviewerRole == BoatOwner` for that marina. `Marina.AverageRating` and `Marina.ReviewCount` updated in-process and synced to the Marina ES document.
- BoatOwner rating = average of all `Score` values where `ReviewerRole == PlaceOwner` for that user. `ApplicationUser.AverageRatingAsBoatOwner` and `ReviewCountAsBoatOwner` updated in-process.

**New entity — `Review` (BaseEntity):** `Id`, `BookingId` FK, `ReviewerId` FK → `ApplicationUser`, `ReviewerRole` (`ReviewerRole` enum — `BoatOwner` | `PlaceOwner`), `Score` (int, 1–5), `Comment` (string?, nullable); unique index on `(BookingId, ReviewerRole)`.

**New enum — `ReviewerRole`:** `BoatOwner`, `PlaceOwner`.

| Ownership enforcement | PlaceOwner actions check `MarinaAdmin` table for `(marinaId, currentUserId)` — not a single FK. Return `Forbid()` (403) if no record found — never 404. |
| RevokeAdmin role cleanup | After removing a `MarinaAdmin` record, check if the user has any remaining `MarinaAdmin` records. If none remain, remove the PlaceOwner role via `UserManager.RemoveFromRoleAsync` — a user with no marinas has no reason to hold the role. |

Any invalid token state (not found, expired, already used) → return `NotFound()` (404) — no information leaked to potential brute-forcers. |

| Dates | `DateOnly` UTC throughout. Client-side JS handles display timezone conversion if needed. |

| Migrations | **Dev is responsible for running `dotnet ef migrations add <Name> --project src/BoatSpotFinder.Infrastructure --startup-project src/BoatSpotFinder.Web` and including the generated `Migrations/` files in the deliverable.** Every entity or EF configuration change requires a new named migration. | Booking cancellation | BoatOwner and PlaceOwner may cancel a `Pending` or `Confirmed` booking only if `booking.StartDate > DateOnly.FromDateTime(DateTime.UtcNow)`. Cancelling on or after `StartDate` is rejected for those roles. **Admin** may cancel any `Pending` or `Confirmed` booking regardless of `StartDate` (support-level override) but cannot cancel `Completed` or already-`Cancelled` bookings. Every Admin cancellation is audited (Phase 2b.5) and notifies both BoatOwner and all marina admins. |

(3) `Spot.PricePerDay` null → fall back to `Marina.DefaultPricePerDay`. `TotalPrice = resolvedPricePerDay × (EndDate − StartDate).Days`. |

| Auto-action | Hangfire recurring job (every 5 min) fires `BookingService.AutoActionAsync()` — finds `Pending` bookings where `booking.CreatedAt.AddHours(settings.AutoActionTimeoutHours) < DateTime.UtcNow` and applies `AdminSettings.AutoActionType` (AutoApprove or AutoReject). |
| Booking completion | Hangfire recurring job (nightly `"0 2 * * *"`) fires `BookingService.CompleteOverdueAsync()` — transitions `Confirmed` → `Completed` where `booking.EndDate < DateOnly.FromDateTime(DateTime.UtcNow)`. |

ES is search-only; SQL Server is source of truth. **ES sync always happens after DB writes succeed.** If ES sync throws, log the error and continue — do not roll back the DB write. The startup re-index job (Phase 3b task 3b.5) recovers any index drift on next deploy. |
| Marina ES doc scope | The marina ES document tracks `Marina.IsActive` only — it does **not** track whether the marina has any active spots. `ToggleSpotActive POST` (Phase 6.2b) and `SpotsController.Deactivate POST` (Phase 3) intentionally do NOT touch the marina ES document. The "has at least one active spot" constraint is applied as a **second-stage SQL filter** inside `IMarinaRepository.GetActiveWithActiveSpotsAsync(marinaIds)`, on top of the ES candidate set in `BrowseController.Index`. A marina whose last active spot was just deactivated will momentarily remain in the ES index but be filtered out at the SQL layer — invisible to end users. This two-stage design keeps the spot-toggle path free of ES round-trips and recovers naturally on the next marina edit or activation toggle. |
| Review window | 14 days from `Booking.EndDate`. Checked in `ReviewService.CanReviewAsync`. After the deadline, `ReviewsController.Create GET` returns 404 — no information leaked. |
| Review immutability | Reviews cannot be edited or deleted once submitted. No Edit or Delete actions on `ReviewsController`. |
| Rating recalculation | Recompute the full average from the repository on each new review — never use incremental deltas to avoid drift. Update `Marina.AverageRating`/`ReviewCount` or `ApplicationUser.AverageRatingAsBoatOwner`/`ReviewCountAsBoatOwner` in the same unit of work as `IReviewRepository.AddAsync`. Sync Marina ES document immediately after. |
| `/security-review` | Required before merging: Phase 5 Tasks 5.5–5.6, Phase 5b Task 5b.6, Phase 6 Task 6.2. |

| Resource | Purpose |

| Container registry | Docker Hub / DigitalOcean Container Registry — app image is pushed here on each build, pulled by k8s on deploy |

### SQL Server Express

- **10 GB/database limit** — ample for this domain at any realistic scale
- **1 GB buffer pool** — the practical RAM constraint; monitor with Kibana if needed
- **Upgrade path:** change `MSSQL_PID=Express` → `Standard` in the pod spec and restart. Same image, same PVC, same connection string. No data migration required.
- **Dev vs. prod:** LocalDB on Windows for local development; SQL Express Linux container in k8s for production.

### Local Development — Three Modes

**Mode 1 — Daily coding** (fastest, no containers)
- `dotnet run` on Windows, connecting to LocalDB
- Use this for all feature work — hot reload, instant feedback
- Elasticsearch not running; ES-dependent features (marina search) stubbed or skipped during this mode

**Mode 2 — Services** (test ES integration without full k8s)
- `docker-compose up` in WSL2 starts SQL Express + Elasticsearch + Kibana
- App still runs on Windows via `dotnet run`, `appsettings.Development.json` points to WSL2 IP
- Use this when working on Phase 3b (ES indexing) or any feature that needs a real DB + ES

**Mode 3 — Full infra** (validate k8s manifests before deploying to DO)
- Build Docker image locally, deploy to k3s running in WSL2 Debian
- Same manifests as production via Kustomize `dev` overlay (no TLS, plain HTTP, lower resource limits)
- Add `127.0.0.1 boatspotfinder.local` to Windows `hosts` file to reach Ingress from browser
- Use this before every push to production

### Kustomize Structure

```
k8s/
  base/                    # shared manifests (deployments, services, PVCs)
  overlays/
    dev/                   # WSL2 local: no TLS, HTTP only, ES heap 256m
    prod/                  # DigitalOcean: cert-manager TLS, full resource limits
```

### docker-compose.yml (Mode 2)

Services: `sqlserver` (`MSSQL_PID=Express`), `elasticsearch` (`ES_JAVA_OPTS=-Xms256m -Xmx256m`), `kibana`. Named volumes for data persistence. Lives at repo root.

### WSL2 Setup Prerequisites

- WSL2 with Debian distro
- Docker Desktop on Windows with WSL2 integration enabled (for image builds)
- k3s installed inside WSL2 Debian: `curl -sfL https://get.k3s.io | sh -`
- `kubectl` configured to point to WSL2 k3s context for infra testing

### Deployment Workflow (per release to production)

1. `docker build` → push image to registry with new tag
2. Apply `db-migrate` Job → wait for completion
3. `kubectl rollout restart deployment/app` → k8s pulls new image, rolls pods
